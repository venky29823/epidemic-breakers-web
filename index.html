How it works

  • Graph: 40 microservices, 111 call edges. Edge u → v means u calls v; slowness spreads from callee to caller.
  • Breakers: each edge watches a noisy stress signal (EMA of callee slowness); it opens for cooldown steps when the signal crosses its threshold θ.
  • GA-optimized: per-edge thresholds evolved by a genetic algorithm with betweenness-guided mutation (full study in the GitHub repo).
  • Oracle reference: θe = min(1, noisee + 0.10) — a reference heuristic: each edge's theta is set from its hidden noise amplitude; not available to any real tuner and not a proven optimum.

Limitations

  • JS port, not the original: the simulator, fitness function and GA here are a faithful JavaScript port of the Python study, but the random streams differ (cyrb53/mulberry32 here vs NumPy there), so exact figures won't match across languages. Cross-language parity is tested in tests/parity.test.js.
  • Small-sample comparisons: the on-page strategy comparison averages over a handful of scenarios. Scenario variance is high — differences smaller than the spread are not meaningful.
  • Oracle is a heuristic: it uses hidden per-edge noise values no real tuner can see, and the +0.10 margin is arbitrary. It marks headroom, not an optimum.
  • One graph: all thresholds were tuned on this specific 40-node / 111-edge call graph. They are not general — a different service topology needs its own tuning run.
